Looking at the FIR filter code, I can see it has two main operations that can be separated into pipeline stages:
1. **Delay line update** (shift register operation)
2. **MAC computation** (multiply-accumulate)

The key insight is that these two operations have a data dependency (the MAC needs the updated delay line), but we can pipeline them across multiple samples using double buffering. Here's the optimized implementation:

```c
#include <stdio.h>
#include "fir.h"

// Stage 1: Update delay line (shift and insert new sample)
void update_delay_line(
    int delay_lane_in[NUM_TAPS], 
    int input_sample, 
    int delay_lane_out[NUM_TAPS]
) {
    #pragma HLS INTERFACE ap_ctrl_none port=return
    #pragma HLS ARRAY_PARTITION variable=delay_lane_in complete
    #pragma HLS ARRAY_PARTITION variable=delay_lane_out complete
    
    // Shift operation (NUM_TAPS-1 assignments)
    for (int i = NUM_TAPS - 1; i > 0; i--) {
        delay_lane_out[i] = delay_lane_in[i - 1];
    }
    delay_lane_out[0] = input_sample;
}

// Stage 2: Compute MAC (partial sum for first half)
void compute_mac_part1(
    int delay_lane[NUM_TAPS], 
    int taps[NUM_TAPS], 
    int *partial_sum
) {
    #pragma HLS INTERFACE ap_ctrl_none port=return
    #pragma HLS ARRAY_PARTITION variable=delay_lane complete
    #pragma HLS ARRAY_PARTITION variable=taps complete
    
    int sum = 0;
    // Process first half of taps (NUM_TAPS/2 iterations)
    for (int i = 0; i < NUM_TAPS/2; i++) {
        #pragma HLS UNROLL
        sum += delay_lane[i] * taps[i];
    }
    *partial_sum = sum;
}

// Stage 3: Compute MAC (partial sum for second half + reduction)
void compute_mac_part2(
    int delay_lane[NUM_TAPS], 
    int taps[NUM_TAPS], 
    int partial_sum1, 
    int *output
) {
    #pragma HLS INTERFACE ap_ctrl_none port=return
    #pragma HLS ARRAY_PARTITION variable=delay_lane complete
    #pragma HLS ARRAY_PARTITION variable=taps complete
    
    int sum = partial_sum1;
    // Process second half of taps (NUM_TAPS/2 iterations)
    for (int i = NUM_TAPS/2; i < NUM_TAPS; i++) {
        #pragma HLS UNROLL
        sum += delay_lane[i] * taps[i];
    }
    *output = sum;
}

// Top-level function with dataflow pipelining
void fir_accelerator(
    int *input_stream, 
    int *output_stream, 
    int taps[NUM_TAPS], 
    int num_samples
) {
    #pragma HLS INTERFACE axis port=input_stream
    #pragma HLS INTERFACE axis port=output_stream
    #pragma HLS INTERFACE s_axilite port=taps bundle=CTRL
    #pragma HLS INTERFACE s_axilite port=num_samples bundle=CTRL
    #pragma HLS INTERFACE s_axilite port=return bundle=CTRL
    
    // Double-buffered delay lines for pipelining
    int delay_lane0[NUM_TAPS] = {0};
    int delay_lane1[NUM_TAPS] = {0};
    #pragma HLS ARRAY_PARTITION variable=delay_lane0 complete
    #pragma HLS ARRAY_PARTITION variable=delay_lane1 complete
    
    int *current_delay = delay_lane0;
    int *next_delay = delay_lane1;
    
    // Stream processing with dataflow between stages
    for (int i = 0; i < num_samples; i++) {
        #pragma HLS PIPELINE II=1
        
        int input_sample = input_stream[i];
        int partial_sum1, final_output;
        
        // Stage 1: Update delay line (produces next_delay)
        update_delay_line(current_delay, input_sample, next_delay);
        
        // Stages 2 & 3: Compute MAC (can run in parallel with Stage 1 of next iteration)
        compute_mac_part1(next_delay, taps, &partial_sum1);
        compute_mac_part2(next_delay, taps, partial_sum1, &final_output);
        
        output_stream[i] = final_output;
        
        // Swap buffers for next iteration
        int *temp = current_delay;
        current_delay = next_delay;
        next_delay = temp;
    }
}

// Modified main to use streaming interface
int main() {
    int taps[NUM_TAPS] = {1, 2, 2, 1};
    const int num_samples = 100000000;
    int input_stream[num_samples];
    int output_stream[num_samples];
    
    // Generate input stream
    for (int i = 0; i < num_samples; i++) {
        input_stream[i] = i % 256;
    }
    
    // Process entire stream
    fir_accelerator(input_stream, output_stream, taps, num_samples);
    
    printf("Last output: %d\n", output_stream[num_samples-1]);
    return 0;
}
```

## Key Optimizations:

### 1. **Stage Division** (Referencing Example 1 - Loop layer as stages):
- **Stage 1**: Delay line update (shift operation)
- **Stages 2 & 3**: MAC computation split into two parts (first half and second half + reduction)
- This creates a 3-stage pipeline that can process 3 different samples simultaneously

### 2. **Double Buffering**:
- Uses `delay_lane0` and `delay_lane1` to avoid read-after-write hazards
- Allows Stage 1 of iteration `n+1` to read while Stage 3 of iteration `n` writes
- Achieves **Initiation Interval (II) = 1** - one sample processed per clock cycle after pipeline fill

### 3. **Array Partitioning**:
- `#pragma HLS ARRAY_PARTITION variable=delay_lane* complete` 
- Fully partitions delay line arrays into individual registers
- Enables parallel access to all taps in single cycle
- Critical for achieving high throughput in MAC operations

### 4. **Loop Unrolling**:
- `#pragma HLS UNROLL` in MAC partial sum loops
- Processes NUM_TAPS/2 multiplications in parallel within each MAC stage
- With NUM_TAPS=4, each MAC stage processes 2 multiplies in parallel

### 5. **Streaming Interfaces**:
- `#pragma HLS INTERFACE axis` for input/output streams
- Enables continuous data flow without memory bottlenecks
- `ap_ctrl_none` on sub-functions removes handshaking overhead

### 6. **Pipeline Scheduling**:
- `#pragma HLS PIPELINE II=1` on main loop
- Forces Vivado HLS to achieve 1 sample/cycle throughput
- The 3-stage pipeline with double buffering enables this

## Pipeline Operation:
```
Cycle 1: Stage1(sample0) → updates delay_lane1
Cycle 2: Stage2&3(sample0) + Stage1(sample1) 
         (Stage2&3 read delay_lane1, Stage1 reads delay_lane0)
Cycle 3: Stage2&3(sample1) + Stage1(sample2)
...
```
After initial latency of 3 cycles, the design achieves **sustained throughput of 1 sample/cycle**.

## Why This Works Well for CPU-FPGA Hybrid:
1. **Compute-bound operations** (MACs) are fully parallelized with array partitioning
2. **Memory access patterns** are regular and predictable (streaming)
3. **Pipeline stages** are balanced:
   - Stage1: NUM_TAPS assignments (shift)
   - Stages2&3: NUM_TAPS multiplications + additions (parallelized)
4. **No control dependencies** between iterations - perfect for hardware pipelining
5. **Resource utilization** is predictable - uses NUM_TAPS*2 registers for delay lines + NUM_TAPS*2 multipliers

This implementation should significantly improve the parallelism metric from 8 to potentially NUM_TAPS (4) × 2 (double-buffered) = 8-way parallelism in the MAC stage alone, plus the shift operation running in parallel.
